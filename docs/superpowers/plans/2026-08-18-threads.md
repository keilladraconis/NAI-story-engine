# Threads Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use subagent-driven-development (recommended) or executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace `WorldGroup` with `Thread` — a commitment with a horizon, a lifecycle, and a lorebook condition that fires when the story has _stopped_ mentioning it — plus the controls that stop threads accumulating.

**Architecture:** The condition is the idea. `not( key <subject> in ['story'] within range N )` is a **forgetting detector**: silent while a thread is alive in the prose, injecting only once the model has dropped it. That inverts the cost model — a thread is free while it is being honoured and spends context only when neglected, which is exactly the moment the old blanket always-on was paying for.

**Tech Stack:** TypeScript (strict), Preact/JSX, vitest, NovelAI script API.

## What this phase does NOT do

**Nothing acts.** Phase 6 owns revise/open/retire/condense. This phase builds the
type, the condition, and the controls; the Engine still only watches and records.
The one exception is the **cap**, which bites immediately because the Forge's
`[THREAD]` command creates threads today.

## The shape

```ts
interface Thread {
  id: string;
  title: string;
  text: string; // the reminder prose — was `summary`
  horizon: "arc" | "plot" | "point";
  entityIds: string[]; // the cast it drags into context
  lorebookEntryId?: string;
  status: "open" | "satisfied";
}
```

`horizon` is an attribute, not three categories. Arc, plot and unresolved point
differ in scope and lifetime, not in kind — all three are "something is open and
wants closing". Three categories would mean three prompts, three sidebar sections,
and permanent misfiling arguments about whether a hidden letter is a plot or a
point. One attribute drives the differences that genuinely exist: condition range,
whether it gets a pacing gate, how eagerly triage proposes retiring it.

### Task 1: `Thread` replaces `WorldGroup`

**Files:** `src/core/store/types.ts`, `src/core/store/slices/world.ts`, and every
file the rename touches — `grep -rl WorldGroup src/ tests/` finds them (8 source,
2 test at time of writing).

The rename is mechanical; the field changes are not:

- `summary` → **`text`**. Same slot, sharper meaning: it is the prose that gets
  injected when the condition fires, not a description of a group.
- **new** `horizon`, defaulting to `"plot"` for anything created without one.
- **new** `status`, defaulting to `"open"`.

`groupCreated` / `groupRenamed` / `groupSummaryUpdated` and their siblings rename
to `thread*`. **No migration** — Story Engine is alpha (CLAUDE.md), and phase 2
already established that upgrading drops Engine state.

Read `src/core/store/effects/handlers/forge-chat.ts:270-302` before you start: the
Forge's `[THREAD]` command is the only thing that creates one today, and it must
keep working. The **verb stays `THREAD`** — only the internal type is renamed.

Tests: the existing `world-select.test.ts` and `hud-model.test.ts` fixtures carry
`WorldGroup`; they move with it. Add one asserting a thread created by the Forge
path lands with `horizon: "plot"` and `status: "open"` rather than `undefined`.

### Task 2: The forgetting detector

**Files:** create `src/core/engine/thread-condition.ts`, test alongside.

**Interfaces:** `buildThreadCondition(thread: Thread, entities: WorldEntity[]): LorebookCondition[]`.

Pure — no `api.v1`, no store. Read `external/script-types.d.ts` for
`LorebookCondition` and its members (`and`/`or`/`not`/`key`/`lore`/`equation`)
before writing anything; **none of `advancedConditions` is used anywhere in `src/`
today**, so there is no house style to follow and the `.d.ts` is the only authority.

The core construction:

```
not( key <subject> in ['story'] within range N )
```

Decisions this task owns, each of which needs a comment justifying it:

1. **What is the subject key?** The thread's title is the obvious candidate and is
   probably wrong — titles are prose ("The hidden letter") and the key is matched
   against story text. Consider the participating entities' names, the title, or
   both. Whatever you choose, a thread whose subject never appears in prose is a
   thread that fires constantly, and one whose subject appears in every paragraph
   never fires at all.
2. **`range` per horizon.** A point decays fast, an arc slowly. Pick three numbers
   and say what each means in paragraphs of ordinary prose — `range` is in
   **characters**, so state your assumed paragraph length.
3. **Gating on participants.** `{type: "lore", entryId}` fires only when that entry
   is active. §4.1 says this is what makes a thread's cast load-bearing: remind
   about the unsettled succession only when a member of the Inner Circle is on
   stage. Decide whether that is an `and` with the forgetting detector, and what a
   thread with **no** participants does.
4. **The arc pacing gate.** §4.3 says `paragraphCount` equations give arc-horizon
   threads a pacing gate. Decide whether that lands here or waits for phase 6, and
   say why.

Test the built structure, not a snapshot: assert the shape has a `not` wrapping a
`key` scoped to `story`, that range varies by horizon, and that a thread with no
participants still produces a usable condition.

### Task 3: The cap

**Files:** create `src/core/engine/thread-cap.ts`; modify `src/core/engine/settings.ts`, `src/core/store/slices/world.ts`.

`threadCap` joins the Engine's per-story settings, **default 8**. Same validation
discipline as the others — read `settings.ts` and match it, and justify the bounds.

**The cap is enforced in the reducer**, not at callsites. That is the same rule as
one-entity-per-lorebook-entry: two callsites will eventually disagree, and a
reducer invariant cannot be bypassed by a new one. `src/core/store/slices/world.ts`
already carries that precedent — read how `entityBound` does it.

`thread-cap.ts` is pure and answers two questions:

- **At the ceiling, which thread gives way?** §4.5 says displace rather than add.
  Satisfied threads should go before open ones; beyond that, decide and justify —
  oldest, shortest horizon, least recently mentioned. Note what information you
  actually have to decide with.
- **Expiry.** §4.5 wants a paragraph-count expiry so an end the story quietly
  abandoned ages out. Decide what "aged out" means with the data a `Thread`
  carries, and be honest in your report if it does not carry enough — that is a
  finding, not something to invent a field for.

### Task 4: Horizon and status in the UI

**Files:** `src/ui/panels/world/ThreadEditPane.tsx`, `src/ui/panels/world/ThreadItem.tsx`, tests.

The pane gains a horizon picker and shows status. Read `SeEntityEditPane`'s
category picker for the established pattern — a thread's horizon is the same shape
of choice.

Rules with history: `onInput` not `onChange`; never dispatch in an input handler;
mount every variant and toggle `display` rather than swapping component types; no
tap debounce; `disabled` is not a re-entry guard.

A satisfied thread should read as satisfied at a glance in the World list without
a second list or a filter — §9.1's "fixed slots" instinct applies here too.

### Task 5: Triage learns the cap

**Files:** `src/core/utils/prompts.ts`, `src/core/engine/triage-strategy.ts`, tests.

§4.5: triage must **justify** a new thread against the cap and **displace** rather
than add at the ceiling. The manifest already carries the thread list; it now
needs the cap and each thread's horizon.

`OPEN` gains no new syntax if you can avoid it — `parseTriage` drops anything it
cannot map, so a richer grammar is a richer set of ways for the model to be
dropped silently. Read Task 5 of the phase-4 plan and `triage-strategy.ts`'s own
notes on why the verb must be uppercase before changing the format.

Nothing executes these intents this phase. The prompt change is so that when
phase 6 turns them on, triage has been asking the right question all along.
